# Job search prompts

These prompts help engineers turn work they have already done into evidence that recruiters, AI sourcing tools, and hiring teams can find and assess. They also support interview review and focused learning. The common thread is specificity: name the system, constraint, decision, trade-off, and result when the source material supports them.

## How to use this folder

1. Open one prompt file and copy its full contents into a new AI conversation as the initial instruction. In a tool that supports system instructions, place it there. For a codebase prompt, give the assistant access to the intended repository; otherwise provide the relevant files or excerpts.
2. Supply the inputs listed below. Replace bracketed placeholders such as `[PASTE GIT LOG OUTPUT HERE]` with your own material. Use a separate conversation for each prompt when possible, especially for the stateful sourcing and interview workflows.
3. Review every generated claim against the source. Verify file paths, commands, metrics, dates, links, and technical terminology before publishing a README or reusing an answer in an interview. Where evidence is missing, add it yourself or leave the gap visible.

| Prompt | What it does | What to provide and how to run it | Job search use |
| --- | --- | --- | --- |
| [Repository README](./repo-readme.md) | Drafts GitHub topics, a short repository description, and a technical `README.md` covering topology, constraints, decisions, reproducibility, and failure modes. | Run it with access to the target codebase, tests, and existing docs. Verify proposed topics and every run or benchmark command before adding them to the repository. | Makes a project easier to find by relevant technical terms and easier for an engineering reviewer to evaluate. |
| [Architecture document](./architecture-doc.md) | Drafts an `ARCHITECTURE.md` describing component boundaries, state, data flow, resilience, and scaling limits. | Run it against the actual codebase. Inspect its claims about concurrency, retries, scaling, and unhandled cases before saving the file. | Gives reviewers concrete evidence of systems thinking and a useful starting point for architecture interviews. |
| [Engineering log: real time](./engineering-log-realtime.md) | Turns notes and a code diff from a recent engineering decision into a dated `LOG.md` entry. | After a work session, paste rough notes or a diff in the prompt's placeholder. Include attempted approaches and test or benchmark results if you have them. | Preserves decisions, trade-offs, and outcomes while they are fresh, providing material for resumes and interview stories. |
| [Engineering log: catch up](./engineering-log-catch-up.md) | Reconstructs a chronological `LOG.md` draft from commit history and pull request summaries. | Paste the requested `git log --reverse --pretty=format:'%h - %ad : %s' --date=short` output and relevant PR or commit summaries. Check any proposed motivation, rejected approach, or integration failure against evidence or your own recollection. | Recovers a usable account of a project's evolution when you did not keep a log during development. |
| [Engineering log: historical](./engineering-log-historical.md) | Surveys a codebase for consequential design decisions, then drafts evidence labeled `LOG.md` entries. | Give it repository access and optional memories. First review its 5–10 proposed decisions and correct them; only then ask it to write the entries. Supply missing history yourself. | Separates what the code proves from what only the author can explain, helping you prepare credible decision stories. |
| [AI sourcing simulator](./ai-sourcing-simulator.md) | Simulates a sourcing parser that combines multiple artifacts and flags unsupported claims, vague language, weak terminology, and missing verification links. | Start a fresh conversation with the prompt. Upload or paste one artifact at a time, such as a resume, LinkedIn profile, repository README, or decision log. Type `RUN ENGINE` after the final artifact to receive the aggregate dossier. | Checks whether your public artifacts support the claims in your profile and whether a machine reader can extract the right signals. |
| [Interview post-mortem](./interview-post-mortem.md) | Reviews an interview recording in either a delivery or technical lane, using timestamped evidence and a scorecard. | Start a fresh conversation, provide an audio or video recording with usable timestamps (or a timestamped transcript), and choose **Delivery & Style**, **Technical Content**, or **Both (Sequential)**. Ask to switch lanes after reviewing the first one. | Identifies specific answers to tighten and moments to rehearse before the next interview. |
| [Mental mapper](./mental-mapper.md) | Explains an unfamiliar technology by mapping its mechanisms to tools you already know, including misleading similarities and a minimal comparison. | Start with the prompt, then name 3–6 technologies you can debug in production, the target concept, and your context and deadline. Follow up on a primitive, failure mode, or debugging scenario. | Helps you prepare for role specific interviews or ramp into a new stack without pretending that similar terminology means identical behavior. |

## A practical sequence

1. **Build the evidence.** Use the real-time log after current work. For older work, choose the catch-up prompt when commit and PR history explain the evolution, or the historical prompt when the code is the main surviving evidence.
2. **Make the repository legible.** Use the architecture and repository README prompts, then edit their drafts until every important claim has a source and every command works.
3. **Check the full candidate picture.** Give the sourcing simulator your resume or profile alongside repository docs and logs. Use its unsupported-claim findings to improve the artifacts or narrow the claim. Its score is a prompt-generated diagnostic, not a measured ranking from a real hiring platform.
4. **Prepare and improve interviews.** Use the mental mapper for unfamiliar concepts, then the interview post-mortem on a recording you can share. Rehearse the specific answers it identifies and compare them with the documented decisions in your projects.

The prompts produce drafts and practice feedback. They cannot establish experience you did not have, recover undocumented motives from code alone, or predict how a particular employer ranks candidates.
